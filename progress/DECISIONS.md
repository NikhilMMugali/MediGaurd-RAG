# MediGaurd RAG — Decisions Log

Record of non-obvious implementation choices, in case a later session needs the "why."

## 2026-10-08 — Python 3.12 instead of 3.14 for the backend virtualenv
The machine's default `python3` is 3.14, but `psycopg2-binary` and several ML packages had no prebuilt wheel for it yet, causing source builds to fail (missing `pg_config`, etc.). Switched to the already-installed Python 3.12 interpreter, which installed every dependency cleanly from wheels. If 3.14 wheel coverage improves later, this can be revisited, but there's no functional reason to chase the newest interpreter here.

## 2026-10-08 — psycopg3 instead of psycopg2
Following from the above: rather than fight `psycopg2-binary`'s build requirements, switched the SQLAlchemy URL scheme to `postgresql+psycopg` and the dependency to `psycopg[binary]==3.2.3`, which ships wheels for 3.12. No behavioral difference for this project's usage.

## 2026-10-08 — bcrypt pinned to 4.0.1
`passlib==1.7.4` reads `bcrypt.__about__.__version__`, which was removed in `bcrypt>=4.1`. Without the pin, every password hash/verify call raised `ValueError: password cannot be longer than 72 bytes` (a misleading downstream symptom of the version-detection failure, not an actual length issue). Pinning `bcrypt==4.0.1` restores compatibility. Revisit if upgrading passlib later.

## 2026-10-08 — SQLite `StaticPool` for Phase 1 tests
`sqlite:///:memory:` without `StaticPool` gives each connection checkout a fresh, empty in-memory database under SQLAlchemy's default pooling, so tables created in one connection are invisible to the next ("no such table" errors). `StaticPool` forces a single shared connection for the test engine, which fixes this without requiring a real PostgreSQL instance just to run Phase 1 tests.

## 2026-10-08 — Role verified against the database on every authenticated request, not just at login
A JWT's `role` claim is treated as a convenience cache, not a trust boundary: `get_current_user` re-reads the user's role from PostgreSQL on every request and rejects if it no longer matches the token. This means a role downgrade takes effect immediately without waiting for token expiry, and a forged/stale token claiming a role the account no longer has is rejected. Chosen because the spec's central rule is that authorization must never be decided from client-supplied or client-cached state.

## 2026-10-08 — Upload endpoint restricted to DOCTOR/NURSE/ADMIN
The original spec says "an authorized user" can upload without naming exact roles for this action. Interpreted conservatively: FINANCE and RECEPTION (who have no clinical access) should not be able to introduce new clinical documents. Revisit if the hackathon demo needs a different uploader role (e.g. a dedicated records-clerk role) — currently ADMIN covers that gap.

## 2026-10-08 — SQLite used for local Phase 2 development instead of PostgreSQL
Neither Docker nor a prebuilt PostgreSQL were available on this machine; `brew install postgresql@16` fell back to compiling from source (no bottle for this host), pulling in a from-source `cmake` build that was still running after 30+ minutes. Per the Phase 2 "speed rule" (development speed matters, fix blockers and continue), local development/demo uses `sqlite:///.../medigaurd_dev.db` for now. This is a configuration choice only: every model, the importer, the knowledge-record generator, and the Alembic migration are plain SQLAlchemy with no Postgres-specific types or SQL, so pointing `DATABASE_URL` at a real PostgreSQL instance (`docker compose up -d postgres`, or once the brew build finishes) requires zero code changes — just re-run `alembic upgrade head` + `scripts/import_synthea.py` against the new URL. Revisit once Postgres is actually available locally and re-verify the acceptance tests against it before the final demo.

## 2026-10-08 — Surrogate UUID primary keys for Synthea tables with no native id
`conditions`, `medications`, `observations`, `allergies`, `procedures`, `immunizations`, `devices`, `supplies`, and `payer_transitions` have no `Id` column in their CSVs. `imaging_studies.csv` *has* an `Id` column, but it repeats across multiple series/instance rows belonging to one study (confirmed by a real `UNIQUE constraint failed` during import) — so it was remapped to a `study_id` column and given its own surrogate `id`. Every other Synthea table keeps its original `Id` as the primary key unchanged, so relationships never need remapping.

## 2026-10-08 — CSV → model column mapping is a blanket lowercase, not a per-table dictionary
Every verified Synthea CSV header lowercases directly onto a model attribute name (e.g. `STATE_HEADQUARTERED` → `state_headquartered`), confirmed by inspecting every header against the models before writing the importer. This kept `scripts/import_synthea.py` to one generic coercion loop keyed off each model's own SQLAlchemy column types (Date/DateTime/Float/Integer) instead of 18 hand-written per-table mappers. `COLUMN_OVERRIDES` exists for the one exception (`imaging_studies`'s `Id` → `study_id`, see above) — add to that dict rather than special-casing the loop if another exception turns up.

## 2026-10-08 — Tailwind pinned to v3, not v4
`npm install -D tailwindcss` installed v4 by default, which moved the PostCSS plugin to a separate `@tailwindcss/postcss` package and replaced the JS config file with a CSS-first `@theme` config — a bigger rewrite than this UI needed. Pinned `tailwindcss@^3.4.0` so the standard `tailwind.config.js` + CSS-variable theme (the shadcn-style convention these hand-written components assume) works without translation. Revisit if the project later wants v4's features specifically.

## 2026-10-08 — shadcn components hand-written, not installed via the shadcn CLI
`npx shadcn@latest init` expects an interactive terminal (prompts for style/base-color/etc.) which isn't available in this non-interactive session. shadcn components aren't actually a package — they're copy-paste source generated by that CLI — so the same files (Button, Input, Select, Card, Badge, Avatar, Dialog, Progress, Textarea, Separator, Label) were written directly in `src/components/ui/` over the underlying `@radix-ui/react-*` primitives, matching shadcn's standard implementation. Functionally identical; just skips the interactive scaffolding step.

## 2026-10-08 — `GET /api/patients` and `GET /api/patients/{id}/status` reuse `retrieve_authorized_sources()`, never duplicate the authorization check
The frontend needed a patient list and a per-patient status without inventing a second security path. `app/rag/pipeline.py` was refactored to split `run_query()` into a reusable `retrieve_authorized_sources()` (authorization + Qdrant filter + search) and the LLM-generation step that follows it. The new patients endpoints call the former directly; the status endpoint classifies deterministically from what actually came back (an authorized "condition" record → "Attention", none → "Stable", denied/empty → "No Recent Information") rather than asking the LLM to self-report a status, which could drift into an unsupported severity claim.

## 2026-10-08 — Qdrant runs in embedded/local mode, not a server
`qdrant-client` supports an on-disk embedded mode (`QdrantClient(path=...)`) that needs no server process at all — exactly the "don't block Phase 3 on infrastructure" instruction, and it happens to make the Qdrant-internals requirement in the problem statement *easier* to demonstrate (same filtering/payload-index engine, zero extra moving parts for a demo laptop). `QDRANT_MODE=server` + `QDRANT_URL` switches to a real server with no code changes. Caveat: the local mode holds a file lock on `QDRANT_PATH`, so only one process (the API server, or a one-off script) can have it open at a time — documented in docs/RAG_DESIGN.md.

## 2026-10-08 — torch/numpy/scipy pinned for this machine's available wheels
Installing `sentence-transformers` pulled in `torch==2.2.2` (the newest wheel available for this Python/platform combination) and `numpy>=2`/`scipy>=1.18` by default, but torch 2.2.2 was built against the numpy 1.x ABI and crashes (`RuntimeError: Numpy is not available`) under numpy 2.x. Pinned `numpy<2` and `scipy<1.13` (the last scipy line that still accepts numpy 1.x) in `backend/requirements.txt`. If a future environment has newer torch wheels available, this pin can be relaxed.

## 2026-10-08 — LLM falls back to a non-hallucinating extractive mode with no API key configured
No LLM provider API key is available in this build environment (hackathon dev box, no secrets provided). Rather than fail every RAG query or fake a response, `app/services/llm_provider.py::get_llm_provider` returns `ExtractiveFallbackProvider` when no key is configured: it returns the single top-ranked authorized chunk's own text, verbatim, cited as `[SOURCE_1]`. This keeps the demo's grounding/citation guarantees intact (it is *impossible* for the fallback to hallucinate, since it never generates new text) while the exact same pipeline code calls a real Groq/OpenAI model the moment `GROQ_API_KEY`/`OPENAI_API_KEY`/`LLM_API_KEY` is set in `.env`. Swap to a real key before the final demo if a more fluent, multi-source-synthesizing answer is wanted.

## 2026-10-08 — Patient-level authorization uses a hard pre-retrieval deny, not a post-hoc filter
Phase 3's spec section 14/36 requires that an unassigned patient's data is excluded "during vector retrieval," and that this be provable, not just empirically true. `app/rag/pipeline.py::run_query` detects a specific patient reference (explicit field or a UUID found in the question text) and, if that patient is not in the caller's `assigned_patient_ids`, returns `DENIED` *before* calling `VectorStore.search()` at all — rather than running the search and discarding a result. This makes "the LLM never saw it" true by construction for that code path, not just true in practice for the fixture data tested.

## 2026-10-08 — PDF → DB mapping uses a rule-based "Label: Value" line parser, not an LLM call
Phase 2's scope is "extract → normalize → validate → store → provenance," not full RAG. A regex-based scan for lines like `Diagnosis: Hypertension` is fast, free, deterministic, and fully testable, and matches the sample document format used throughout the spec. `app/ingestion/pdf_mapper.py::extract_patient_document_data` is the single seam to replace with an LLM-based or ML-based extractor later without touching `map_to_database` or the upload API.

## 2026-10-08 — RAG quality fix: real LLM generation, query classification, recency-aware retrieval
Root cause of poor answer quality was that no `GROQ_API_KEY` had been configured, so every answer came from the extractive fallback (the top retrieved chunk, verbatim) — functionally correct but looked like a broken product in a demo. Fixed in four parts:
1. **Real LLM wired up.** `GROQ_API_KEY` set in `.env` (not committed; `.env.example` documents the variable names only). `llm_model` default changed from `llama-3.1-70b-versatile` (decommissioned by Groq) to `openai/gpt-oss-120b`, verified live against this account's `/v1/models` listing. `ExtractiveFallbackProvider` renamed `DevModeProvider` and its message changed from "looks like a real answer" to an explicit `[DEV MODE] ... generation is currently unavailable` statement — a misconfigured box now fails loud, never pretty. A new `_SafeProvider` wrapper catches any vendor-call failure (bad key, rate limit, decommissioned model) and degrades to the same explicit dev-mode message instead of a 500.
2. **Query classification.** `app/rag/query_classification.py` is a small deterministic keyword matcher (not an LLM call) mapping a question to candidate `record_types` (medication/condition/encounter/claim/observation/allergy) and, for observations, to Synthea's own `category` field (vital-signs/laboratory/exam/imaging/procedure/therapy vs. survey/social-history). A clinical role's bare "recent observations" now excludes socioeconomic survey rows by default; an explicit "lab results" or "vitals" question narrows further. Classification output is always intersected with `AuthorizationContext.allowed_record_types` before touching retrieval — it only ever narrows, never widens, what a role can see. A question that matches a domain the role has zero access to produces a role-appropriate denial ("Clinical observation information is not available for your current role.") instead of a generic empty-results message. A question naming two domains at once (e.g. a Finance user's "diagnosis and claim balance") unions all matched types rather than picking one, so the authorized half of a mixed question still gets answered.
3. **Recency.** `knowledge_records` gained `record_date` (the event's own date — Observation.date, Condition.start, etc. — not ingestion time) and `observation_category`, backfilled for all 176k existing rows via `scripts/backfill_knowledge_metadata.py` (correlated SQL `UPDATE`, seconds not hours) and populated going forward by `app/services/knowledge_generator.py`. The known-patient fast path (`_retrieve_for_known_patient` in `app/rag/pipeline.py`) blends relevance and recency when the question contains "recent/latest/current/newest": candidates are pulled date-sorted from SQL, then ranked by `0.5*cosine + 0.5*recency_rank` rather than recency alone overriding relevance or vice versa.
4. **Clean context, clean citations.** The LLM now receives `[SOURCE_n]` blocks built from structured fields (content + observation category) rather than the answer *being* a raw chunk. Citations resolve `source_document_id` (a UUID FK) to the actual `SourceDocument.file_name` via one batch query instead of leaking the raw id, and carry the record's own date so the frontend shows "Observation record · 12 Sep 2026" instead of a raw record UUID (`ChatMessage.tsx::citationLabel`).

Scope deliberately left out: the general (no-detected-patient) retrieval path gets record_type narrowing from classification but not observation-category filtering, since that payload field isn't backfilled into existing Qdrant points (only SQL `knowledge_records`) — acceptable because the primary UX path always has a selected-patient context (item 6 of the fix request), and re-embedding 176k points for a payload-only metadata addition isn't worth the cost versus a targeted `set_payload` pass, which can be done later if the general path's quality matters more than today.

## 2026-10-08 — Clean 100-patient dataset: a display_id column, not a primary-key remapping
Replacing the raw Synthea UUID shown in the UI with a clean "P001" id could have meant renaming every patient-referencing primary/foreign key in the schema (conditions.patient, observations.patient, claims.patientid, knowledge_records.patient_id, patient_assignments.patient_id, ...) — a large, risky rewrite touching the authorization-critical retrieval path for a purely cosmetic change. Instead, `Patient.display_id` is a new, independent, unique column; `Patient.id` stays the real internal id everything else already points to. `app.rag.pipeline.resolve_patient_reference()` is the one place that turns a UI-facing Pxxx (or a legacy raw UUID, for back-compat) into the internal id before any authorization check or query runs — every other function in the authorization/retrieval path is untouched and still deals purely in internal ids, exactly as before this change.

## 2026-10-08 — Hybrid retrieval: deterministic structured answers skip the LLM entirely, not just Qdrant
The PS's grading criteria and the "chat looks like raw database output" complaint both point the same direction: a question like "what medications is this patient taking" has one exact, enumerable answer sitting in a SQL table — asking an LLM to phrase it adds latency, cost, and a (small but nonzero) hallucination surface for zero benefit. `app/rag/query_classification.py` now classifies a `route` (structured/summary/semantic) alongside `record_types`; `app/rag/structured_answers.py` builds the final markdown answer and citations directly from SQLAlchemy rows for identity/medication/condition/allergy/procedure/encounter/finance/recent-observations questions — `run_query` never calls Qdrant or the LLM provider for these. The semantic path (Qdrant + LLM) is kept only for genuinely open-ended/contextual questions (nothing in the demo corpus is policy-document-shaped yet — see "Scope decision" below). Authorization is identical either way: `_authorize_and_classify()` computes the same role/record-type/patient-assignment checks once, and both routes start from its result, so there is still exactly one retrieval-authorization code path.

## 2026-10-08 — Scope decision: no hospital-policy document corpus built
The task's sections on policy/guideline questions ("what does the infection-control policy say") assume a second knowledge source — public hospital policy PDFs, chunked and indexed with their own authorization story (public to every role, unlike patient data). Building that pipeline (sourcing real public policy PDFs, section/page-aware chunking, a new sensitivity tier) is a genuinely separate feature, not a tweak to the existing patient-data RAG path, and the PS's core grading criteria (multi-modal structured+PDF ingestion, retrieval-time authorization, citation grounding) are already fully demonstrated by the existing uploaded-patient-PDF pipeline. Skipped for this iteration rather than half-built; a policy-style question with no matching patient/record-type classification falls through honestly to "I couldn't find enough authorized information" rather than fabricating an answer. Revisit only if there's spare time before the demo — tracked in progress/TODO.md.

## 2026-10-08 — Observation category filtering happens at knowledge-generation time, not via a new DB column
`Observation.category` already existed (Synthea's own field) and was already backfilled onto `knowledge_records.observation_category` in the prior RAG-quality-fix session. Rather than adding yet another "is this indexable" flag, `scripts/generate_knowledge_records.py`'s observation generator simply queries `Observation.category.in_(CLINICAL_OBSERVATION_CATEGORIES)` before creating knowledge records — survey/social-history/uncategorized rows are never inserted into `knowledge_records` at all, so they can never reach Qdrant or the LLM, while remaining fully queryable in the structured `observations` table for any direct DB lookup that genuinely needs them.

## 2026-10-09 — PDF retrieval fix: root cause and what changed

A real uploaded lab report (a 10-page haemogram/lipid/thyroid panel) reproduced an exact, reportable bug: upload "succeeded" (`status: COMPLETED`), but asking "tell me about <patient name>" answered "the provided records do not contain any information about" that patient — while still showing five completely unrelated patients' Procedure records as "Sources" underneath that answer. Reproduced with a synthetic fixture matching the real document's structure (not the real file — see "no real PDFs/PHI in Git" below) and traced to four independent, compounding gaps, all now fixed:

1. **Zero knowledge records for non-Label:Value content.** The PDF mapper only ever created a `knowledge_records` row when a page matched one of six hardcoded categories (`diagnosis/condition`, `medication`, `allergy`, `procedure`, `encounter/visit`, `billing/outstanding/claim`). A lab report's test-result tables match none of these, so `map_to_database` created zero structured rows AND zero knowledge records — the document was completely unretrievable despite the upload response looking successful. Fix: every page's own extracted text is now *also* kept as a generic `record_type="document"` narrative knowledge record, unconditionally — see `app/ingestion/pdf_mapper.py`'s module docstring. `"document"` had to be added to `CLINICAL_RECORD_TYPES` (`app/authorization/context.py`) or no role's `allowed_record_types` would ever include it.
2. **Identity extraction garbled by a packed header line.** The per-line "Label: Value" parser captures everything from the first colon to end-of-line as the value. A real lab report's header line — `"Name : HETBHAI PATEL Reg. No. : 50803400728"` — has two fields on one physical line, so the naive parser stored the patient's "last name" as `"PATEL Reg. No. : 50803400728"`. Fix: `_extract_identity_fallback` is a field-boundary-aware regex pass (stops at the next known label keyword, not just end-of-line) used whenever the naive capture looks garbled (contains a colon, or is implausibly long) — generic to any document using a multi-field-per-line layout, never keyed to this specific patient's name. Also recovers gender, and recognizes "Reg. No."/"Registration No."/"MRN" as patient-id-label synonyms (useful for correct re-upload dedup on real hospital/lab documents).
3. **No free-text patient-name resolution at all.** `resolve_patient_reference` only ever recognized a `Pxxx` display id or a pasted UUID. "Tell me about Hetbhai Patel" had no resolution path whatsoever and silently fell through to an *unscoped* semantic search — no patient filter applied at all, searching across every patient the role can see. Fix: `_resolve_patient_by_name` added as a fallback — exact, normalized full-name match against real `Patient` rows. A false/no match simply fails to resolve (same as today's behavior when nothing matches); it can never grant access beyond what the unchanged post-resolution authorization check already allows.
4. **Relevance threshold silently inert.** `VectorStore.search()` had `score_threshold=score_threshold or None` — Python falsiness, not a deliberate "disabled" sentinel — which discarded the configured threshold whenever it was `0.0`, which was also `RAG_SCORE_THRESHOLD`'s own default. No relevance floor was ever actually applied by any caller, so an unscoped search (gap 3) always returned its top-k regardless of how unrelated those results actually were. Fix: removed the falsy-coalescing (`None` is the real "no filter" value now) and changed the default to `0.35` (cosine; embeddings are normalized). Applied both to the Qdrant-search branch and to the known-patient SQL fast path's own dot-product ranking (skipped specifically for recency queries, where the score is dominated by recency rather than topical similarity).

**Also fixed as part of the same pass:**
- Duplicate-upload handling used to be a dead end — any repeat of an already-seen file hash returned `409` unconditionally, even if the existing document (predating this fix, or a prior indexing failure) had zero actual knowledge records. It now verifies the existing document's real indexed state and repairs it in place (regenerates + indexes its narrative knowledge records against the *same* `document_id`) instead of re-raising the same unhelpful `409` — see `app.api.upload._handle_duplicate_upload`.
- Citations gained `document_id` and `evidence_text` fields (both `Citation`/`CitationResponse`), needed for the new citation → PDF viewer feature (section 10) — a citation previously carried only a display `file_name`, with no way to actually fetch the underlying PDF.
- A new `GET /api/documents/{document_id}/file` endpoint streams the original PDF for the viewer, authenticated and `_document_authorized`-checked identically to every other document endpoint — never an unauthenticated static route.
- A right-side PDF viewer panel (react-pdf/pdf.js) opens on citation click in Clinical Chat, jumps to the cited page, and attempts text-layer highlighting of the citation's `evidence_text` — skipped for a whole-page narrative citation (highlighting "the whole page" isn't a useful visual cue), where the panel instead shows the full evidence text below the rendered page.

**No real PDFs/PHI in Git**: the regression tests and reproduction in this session use synthetic fixtures (`tests/test_pdf_retrieval_fix.py`, `tests/test_upload.py`) built to match the real document's *structure* (multi-field header line, lab-table layout) with fictional names/ids — never the actual uploaded file or its real extracted text.

**Known limitation**: a patient record created *before* this fix (from a document uploaded prior to 2026-10-09) keeps whatever garbled name the old parser stored — there is no data-migration script to re-run identity extraction against already-ingested patients. Only newly-uploaded documents benefit from the corrected extraction; re-uploading an old document only repairs its *indexing* state (gap 1), not a patient row's already-stored name fields.

## 2026-10-10 — PDF retrieval fix, part 2: a real user upload found two more gaps

A real demo PDF (`MediGaurd_Demo_Patient_Report.pdf`, 3 pages, patient "Kavya Demo Patient") was uploaded through the live app and reproduced the exact same class of bug via two causes the first pass (above) didn't cover:

1. **A third identity layout the first fix's two regexes still couldn't parse.** This document renders each field label alone on its own line, with the value on the line immediately after — no colon anywhere (`"Patient Name"` / `"KAVYA DEMO PATIENT"` / `"Demo Patient ID"` / `"DEMO-PT-2026-1042"`). Both `_LABEL_LINE` (needs a colon) and `_extract_identity_fallback` (also colon-anchored) are structurally incapable of matching this — confirmed via the upload response itself: `"no patient could be identified in it — 0 record(s) created, 3 chunk(s) indexed"`. Fixed with a third fallback tier, `_extract_label_next_line_fields` — scans consecutive line pairs for a known label on one line and a value on the next, generic to the layout.
2. **Duplicate-upload repair (part 1's own fix) only checked "zero knowledge records" as the sign of brokenness.** This document had 3 real knowledge records (page-level narrative chunks, correctly created by part 1's fallback) but `patient_id: None` on all of them and on the `source_documents` row — a different broken state the repair logic didn't recognize at all, so re-uploading reported "already uploaded and fully indexed," never attempting to resolve the patient. Fixed: `_handle_duplicate_upload` now treats `existing.patient_id is None` as an independent repair trigger, re-running identity extraction, linking/creating the patient, backfilling `patient_id` onto any existing knowledge records that had `None`, and critically **re-indexing those records into Qdrant** — the payload's `patient_id` is baked in at upsert time, so correcting only the SQL row would leave Qdrant's copy stale and the patient-scoped retrieval path still blind to it. Qdrant upsert is idempotent on the knowledge_record's own stable id, so this is a safe overwrite, not a duplicate.

**A third thing found while verifying the above live** (not a new report, caught during this session's own verification): the known-patient SQL fast path (`_retrieve_for_known_patient`) had inherited the *same* relevance-score floor added in part 1 for the unscoped cross-patient search. Once this document's patient was correctly linked, "Tell me about Kavya Demo Patient" worked, but a specific content question ("Which value is flagged LOW and what is its printed reference interval?") came back "couldn't find enough information" — `debug.candidate_count: 3` confirmed all three of this patient's own, correctly-scoped page chunks were found, then all three were discarded by the 0.35 floor, because a coarse whole-page chunk covering CBC + chemistry + thyroid + vitamins dilutes its cosine similarity to any one short, specific question below that bar. The floor is not a security boundary on this path — every candidate there is already scoped to the right `patient_id` AND `record_type` AND `allowed_sensitivity` by the SQL query itself, before any ranking happens — so it was only ever trading away correct answers for nothing. Removed from `_retrieve_for_known_patient`; it remains on the unscoped Qdrant-search branch, which is where the actual originally-reported cross-patient leakage happened and where the floor is the real fix.

**Verified against the real document** (not a synthetic reconstruction this time — the actual file the user uploaded was still on disk at its `storage_path`, so the repair was exercised and verified against the real bytes): re-upload → `"linked it to patient P105 and re-indexed its existing chunks with the corrected patient association"` → "Tell me about Kavya Demo Patient" → `ANSWERED`, citations all `patient_id: "P105"`, no more unrelated sources → "What is the WBC count..." → `6,200 cells/µL, page 1` → "Which value is flagged LOW..." → `25-OH Vitamin D, 18 ng/mL, reference 30-100 ng/mL, page 3` → unassigned nurse asking the same question → still correctly `DENIED`. 3 new/updated tests, 52/52 backend tests passing.

## 2026-10-10 — Query classification robustness pass (master audit, phase 5)

The audit's own phase 5 examples were reproduced directly against `classify_query()` before any change (per rule "reproduce bugs before fixing them"), surfacing 7 concrete failures:

1. **"what meds is he taking"** — `meds` shares no prefix with `medication`, so the existing `medication\w*` suffix trick never covered it. Fixed by adding `meds?` as its own alternative in the medication rule.
2. **"what about his blood report" / "value for vitamin D"** — the lab rule only matched `lab\w*|laboratory|test result\w*`; real phrasing for the same Synthea `Observation` data ("blood report", "blood work", "vitamin D") fell through to unscoped semantic. Added `blood (test\w*|report\w*|work)` and `vitamin\w*`.
3. **"any flagged values" / "what's abnormal in the labs"** — Synthea's `Observation` rows carry no flag/abnormal concept at all (that text only exists inside a PDF's own printed "NORMAL"/"LOW" narrative); routing this to the structured `answer_recent_observations()` handler would silently ignore the real evidence. Added as a new rule with `intent_kind="general"` (deliberately excluded from `_STRUCTURED_INTENTS`) so it still narrows `record_types` to `["observation"]` for retrieval scoping but always resolves via the semantic path, which can actually read the document text.
4. **"wat medicatoin does she take"** — a real typo, not a synonym gap. Added a bounded, last-resort typo-tolerance layer (`_typo_tolerant_fallback`, stdlib `difflib.get_close_matches`, cutoff 0.8, words ≥5 chars, matched only against a small fixed domain-word vocabulary) that runs *only* when every regex rule above matched nothing — it can never override a real match or reclassify against patient names/arbitrary text. This is NOT an ML model and nothing was trained; it is one more deterministic lookup table. One case is a known, deliberately unrecovered gap: "alergic" (missing double-L) has a fuzzy ratio (~0.71) below the 0.8 threshold — loosening the cutoff to catch it risks false-positive reclassification elsewhere in the vocabulary, so it's left as a documented limitation (`test_known_typo_tolerance_limit`), not patched.

Added `backend/tests/test_query_classification_eval.py` — a 40-case golden evaluation set (not a training set) covering structured/summary/identity/semantic routing, multi-domain questions, case/punctuation insensitivity, and the typo-tolerance boundary. 40/40 passing.

**Self-caught regression**: the new "flagged" rule's `record_types=["observation"]` narrowing broke an existing test (`test_known_patient_fast_path_has_no_relevance_floor` in `test_pdf_retrieval_fix.py`) whose fixture knowledge record was `record_type="document"`, not `"observation"` — the now-correctly-scoped SQL query legitimately found zero candidates, which is a different, correct behavior than what that test was actually trying to isolate (whether a relevance floor applies on the known-patient path). Fixed by changing the test's question to one that triggers zero classifier rules, cleanly separating the two properties. **Known limitation, documented rather than fixed**: the backend has no server-side conversation memory — every `/api/rag/query` call is independently authorized and answered with no access to prior turns' questions or answers (this is itself a correct security property: context can never leak from a cached prior-turn state).
